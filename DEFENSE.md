- [Готовый сайт komnata 2.0](https://sambersi.github.io/komnata-docs/).
- [Репозиторий и файлы](https://github.com/Sambersi/komnata-docs).
- [Подробный отчёт REPORT.md](https://github.com/Sambersi/komnata-docs/blob/main/REPORT.md).
- [PR №1: проверки и исправления](https://github.com/Sambersi/komnata-docs/pull/1).

- [Все запуски Actions](https://github.com/Sambersi/komnata-docs/actions).

Публичный сайт и отчёт открываются без входа в аккаунт.
Для просмотра некоторых журналов GitHub может попросить войти в аккаунт.
Устанавливать Git, Python и MkDocs для показа результата через интернет не нужно.
В архиве для переноса есть автономная страница со всем руководством и HTML-отчёт: их можно открыть двойным щелчком без сервера.
Полный сайт MkDocs также сохранён, но для него предпочтителен HTTP-сервер; для показа без установки используйте автономную страницу.
Копия Python-окружения не нужна для показа и не включена в архив.

## Сценарий показа на 5–7 минут

1. Откройте сайт и скажите: «Это документация вымышленного сервиса бронирования komnata 2.0. Программу запускать не требовалось; эталон задан файлами product/ и CHANGELOG».
2. Откройте REPORT.md, таблицу задания 1: покажите старый порт 8080, команду start и удалённый cache_ttl; рядом откройте их правильные значения в источниках.
3. В PR №1 откройте историю проверок: [Vale упал](https://github.com/Sambersi/komnata-docs/actions/runs/44390751566), затем [упала строгая сборка](https://github.com/Sambersi/komnata-docs/actions/runs/44391318648), затем [всё прошло](https://github.com/Sambersi/komnata-docs/actions/runs/44391713043).
4. На сайте откройте «Проверка конфигурации»: покажите --config и объясните, почему нет --fix, выдуманных кодов возврата и обещанных номеров строк.
5. Откройте PR №2 → Files changed: покажите одно предложение на строку и таблицу проверки ИИ в отчёте.
6. Покажите configuration.rst и сравните с configuration.md; объясните роль Sphinx :doc:.
7. В отчёте покажите выбор инструментов, стратегию снимков и три метрики; в конце честно обозначьте ограничение взаимного ревью.

## Ответы на контрольные вопросы

### Что даёт Docs as Code и какова цена?

Git хранит историю и позволяет увидеть автора и причину правки; PR даёт обсуждение до публикации; CI воспроизводимо проверяет и публикует страницы.
В этой работе исправления видны отдельными коммитами, а не только в готовом файле.
Цена — настройка YAML, зависимостей, правил и работа с ветками; содержательный контроль всё равно нужен.

### Почему битая ссылка найдена, а неверный порт нет?

MkDocs видит, что configure.md отсутствует среди файлов.
Число 8080 само по себе допустимо, а правильный порт 8000 находится в отдельном эталоне.
Чтобы находить это автоматически, нужна дополнительная проверка по схеме или данным продукта.

### Почему сначала было видно только Vale?

Шаги GitHub Actions по умолчанию запускаются после успеха предыдущих.
Vale вернул 1 и остановил дальнейшие обычные шаги.
Для MkDocs добавлено if: always(), чтобы получить оба результата; неуспешный build по-прежнему не допускает публикацию.

### Error и warning действительно отличаются?

В Vale 3.24.0 проверено на временном файле: запрещённый термин дал error и код 1, жаргонное предупреждение — warning и код 0.
Временный файл удалён, журнал эксперимента отражён в отчёте.
Успех CI сам по себе не равен защите main: для принудительного запрета слияния нужна отдельная настройка ветки.

### Зачем фиксировать версии?

requirements.txt задаёт конкретные MkDocs 1.6.1 и Material 9.7.7, поэтому новая основная версия генератора не выбирается автоматически.
Красный баннер темы — предупреждение о будущей совместимости, а не ошибка текущей сборки.
Транзитивные зависимости полностью не зафиксированы; полная воспроизводимость требует дополнительного lock/constraints и контролируемого обновления.

### Что такое источник истины и что делать с противоречием?

Это согласованный эталон: справка команд, default YAML, требования и журнал изменений.
При противоречии сначала уточняют целевую версию, фиксируют расхождение и задают вопрос владельцу продукта.
Нельзя подгонять эталон под написанный текст или молча выбирать удобный вариант.


### Почему reStructuredText на GitHub не равно Sphinx?

reStructuredText — язык разметки, Sphinx — генератор с дополнительными ролями и картой документов.
Роль :doc:`usage` требует Sphinx и существующей страницы проекта; просмотрщик GitHub не заменяет такую сборку.

### Почему не оставить одну документацию для всех версий?

Клиенты 1.4 ещё пользуются старой версией, а команды и параметры 2.0 уже изменились.
Снимки сохраняют правильные инструкции для каждой поддерживаемой версии.
Удалённый cache_ttl не возвращается в текущую таблицу; в старой версии его описание сохраняется только после проверки по её эталонам.

### Какая метрика самая важная?

Одной недостаточно: быстрая публикация может быть неточной, отсутствие ошибок линтера не означает понятности, а пользовательский тест может быть слишком лёгким.
Поэтому выбраны процессная задержка, содержательные дефекты и успех выполнения сценария; ограничения каждой записаны в отчёте.
